# 025 - Replay Mode

2026-07-09

## Context

Step 3 of the solution/save/replay roadmap (move recording → headless
validator → **replay mode** → solved-solution persistence → mid-level
save/load). The user asked for this deliberately *better* than the
original's own replay, which always runs at one fixed fast pace with no
pause/step/speed control at all (`legacy/src/level/LevelLoading.cpp`'s
`loadReplay()` just sets `m_loadSpeed = 1` and lets it run unattended).
Requirements: starts playing at normal speed immediately, a step counter
(like the original's `Pedometer`), Pause/Step/Play/Fast-forward controls
with media-player glyphs, and only fish animation + background music play
- no dialogs, no item decorative animation, no sound effects/dialog voice.

Level-solved persistence (step 4) isn't built yet, so there's no in-app
source of "the player's own solved run" - per the user's own choice
(AskUserQuestion), this launches from normal play via a keyboard shortcut
(`P`), using the already-validated `legacy/solution/<level>.lua` reference
solution (docs/022-024, 79/81 levels solve cleanly) as the move data. A
deliberate, temporary bridge - step 4 will supply a player's own recorded
solution the same way later.

## Key mechanism: round-by-round, not the fast validator

`GameEngine.loadMove()`/`Room.loadMove()` (docs/022) already exist, but
fast-forward through any pending falls instantly before applying a move -
correct for headless validation, wrong for a *watchable* replay (would
skip the falling animation entirely). Replay needed the same round-by-round
shape live play already uses (`Room.nextRound()`), just sourcing "was a
move attempted this round" from a recorded move string instead of
keyboard/mouse - so `Room.replayRound(symbol)` mirrors `nextRound()`
exactly (`beginFall()`, then only consume `symbol` if `isFresh()`, via
`Controls.makeMove(symbol)` from docs/022), returning whether it was
actually consumed so the caller knows when to advance its move index.
`GameEngine.tickReplay()` wraps it. `nextRound()`/live play are untouched.

Verified this produces the *same* outcome as the fast validator before
building any UI on top of it: drove `tickReplay()` round-by-round for
`cannons` (39 moves) and `airplane` (235 moves) and got `solved: true` for
both, matching docs/024's independently-confirmed validator results.

## What was built

- **`web/src/scenes/sceneUtils.ts`** (new): `pictureToAssetUrl`,
  `isFishKind`, `resolveInitialTextureKey` lifted out of `LevelScene.ts`
  (were module-level functions there) so `ReplayScene` can reuse them
  without one scene importing from another's file. `LevelScene.ts` now
  imports them back; behavior unchanged.
- **`web/src/game/Room.ts`** / **`GameEngine.ts`**: `replayRound(symbol)`
  / `tickReplay(symbol)` - see above.
- **`web/src/lua/levelLoader.ts`**: `extractSavedMoves(source)` - the
  `saved_moves = '...'` regex the docs/022-024 scratchpad scripts already
  used, now a real exported helper.
- **`web/src/scenes/ReplayScene.ts`** (new): structured like `LevelScene`
  (background/model sprites, one `ModelAnimator` per model, `AudioManager`,
  a generation-guarded `createLevelScript()` bootstrap - identical pattern
  to `LevelScene.startEngine()`), but with a replay-specific tick and UI
  instead of live input:
  - `init(data: { levelData, moves })` - Phaser's dynamic scene-data
    pattern, since the move string isn't known at `main.ts` boot time.
  - Starts in **normal-speed play** immediately on `create()` - the user's
    first requirement - via a `Phaser.Time.TimerEvent` at `ROUND_MS`,
    exactly live play's own cadence.
  - **Speed control**: Pause removes the timer; Play recreates it at
    `ROUND_MS`; Fast recreates it at `ROUND_MS / 6`. Step forces one manual
    `tick()` while paused. All four reuse the *same* per-round `tick()`
    body - fast mode is the identical round-by-round simulation firing
    more often in real time, not a separate "jump to end" path.
    `ModelAnimator.sync()` already defensively kills/snaps any in-flight
    tween before starting the next one (docs/010), so faster round-firing
    just makes slides shorter/choppier at high speed rather than stacking.
  - **Tick body**: consumes the next queued symbol via `tickReplay()`,
    still runs `levelScript.tick(renderModels)` every round (needed so
    level-specific music commands - including mid-level stops like
    `viking1`'s musician gag - keep firing correctly), but applies *only*
    `getMusicCommand()`. Deliberately does not: display
    `getActiveSubtitle()` (no subtitle text object exists in this scene at
    all), play `getPendingSoundEffects()` (still *drained* every round so
    the array doesn't grow unbounded over a 2000+ move replay, just
    discarded), play impact/death sounds, or apply any non-fish model's
    `getScriptAnim()` override (items still visually move/fall via core
    physics - that's the puzzle actually being solved, unavoidable and
    expected - they just never show Lua-driven decorative animation
    swaps). Fish animation is unaffected either way - it never reads
    `getScriptAnim()` regardless (docs/009/013).
  - **UI**: a step-counter text (`"42 / 235"`, top-right) and four
    clickable buttons using standard media-player Unicode glyphs - ⏸ ⏭ ▶
    ⏩ - with the active mode highlighted (green background). Auto-pauses
    and shows "Solved!" on `isSolved()`, a death message on
    `!isSolvable()`, or just stops cleanly if the recorded moves run out
    without solving.
  - `R` restarts the replay from move 0 (auto-resumes normal-speed play,
    matching the "starts playing immediately" requirement applying on
    restart too); `Escape` returns to normal play
    (`this.scene.start("level")`).
- **`web/src/scenes/LevelScene.ts`**: new `keydown-P` handler - fetches
  `legacy/solution/<levelName>.lua`, parses it with `extractSavedMoves`,
  calls `this.scene.start("replay", { levelData, moves })`. Guarded
  against double-firing while the fetch is in flight. Status text gained
  "P = watch reference solution replay".
- **`web/src/main.ts`**: registers both scenes - `scene: [new
  LevelScene(levelData), ReplayScene]`.
- Both scenes gained a `SHUTDOWN` handler stopping their `AudioManager`
  (and `LevelScript`) on the way out - Phaser's Sound Manager is
  game-global, not scene-scoped, so switching scenes without this would
  leave the outgoing scene's music playing underneath the incoming one.
  This is the first time this project has had more than one active scene
  to switch between, so the gap was latent but harmless until now.

No changes to live play's `nextRound()`/`Controls`/`MouseControl`/physics.

## Verification

- `npx tsc -b` clean.
- Direct engine-driven cross-check (above): `tickReplay()` round-by-round
  reaches the same `isSolved()` outcome the fast validator already
  confirmed, for both a short and a long solution.
- Real-browser check (temporary `window.__game` hook, removed after):
  - `airplane`: `P` launches replay, immediately playing at normal speed
    (step counter advancing ~1 step/130ms, music audible), Pause freezes
    the counter exactly, Step advances exactly one, Fast measurably sped
    up progress (9→51 steps in 1s vs ~8 steps in 1s at normal - roughly
    the targeted 6x), fast-forwarded to completion and confirmed it
    stopped cleanly at "235 / 235" / "Solved!".
  - `viking1`: full 119-move replay via Fast, reached "Solved!" cleanly.
    Its scripted music-stop gag (`docs/018`) did *not* fire in this run -
    traced why before assuming a bug: the stop is a random 300-700-*round*
    countdown, and this solution's 119 moves only span roughly 119-150
    rounds (replay stops as soon as the puzzle is solved, per the "ran out
    of moves"/`isSolved()` checks in `tick()`), well under the threshold.
    Not a gap in the replay's music handling (it reads `getMusicCommand()`
    every round through the same live-Lua path docs/018 already verified
    end-to-end over 800 rounds) - just this particular solution doesn't
    run long enough in round-terms to reach that particular gag.
  - Screenshot confirmed the UI renders correctly: step counter, status
    text, all four buttons, Play button visibly highlighted while active.
  - `R` correctly reset to move 0 and resumed normal-speed play; `Escape`
    correctly returned to `LevelScene` (`levelActive: true, replayActive:
    false`).
  - Zero console/page errors throughout every check.
- Regression: normal `LevelScene` play (held movement, mouse pathing,
  Space switch, R restart) re-verified clean after the `sceneUtils.ts`
  extraction.

## Open for next time

- Step 4 (solved-solution persistence) will eventually replace "always
  replays the uploaded reference solution" with "replays the player's own
  best solved run," reusing this same `ReplayScene`/`tickReplay()`
  machinery unchanged - only the move-string *source* changes.
- The `6x` fast multiplier is a guess, not measured against anything -
  easy to retune (`FAST_MULTIPLIER` in `ReplayScene.ts`) once it's
  actually watched more.
- No handling yet for a replay that gets stuck (a queued symbol never
  consumed for many consecutive rounds) beyond the counter simply not
  advancing - not expected given 79/81 solutions are validated, but worth
  a real "this replay appears stuck" message later if it ever comes up.
