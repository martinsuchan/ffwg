# 019 — Performance: compact state store, fast path, parallel expansion (P1, P2, P4)

The review's three performance items, each measured with `ffsolve bench --suite`
and guarded by the regression suite (docs/015, docs/017).

## P1 — memory, and the growth stalls

`StateSet` + a separate node array cost 95-202 bytes per stored state, and every
array doubled by copying. On long runs the copies were where searches died: every
`results.csv` run that hit its time limit near 2^24 or 2^25 states had spent most
of its budget stalled in a resize - society reached 24.8 M expansions in a 360 s
and a 900 s run alike.

- **`StateStore`** (main solver only): one index per state serves as node too -
  no key offset (implicit), no stored hash (recomputed when buckets grow), cost and
  estimate in 16 bits, the move as a symbol index. Storage is **chunked** (16,384
  states a chunk): growing allocates a chunk and copies nothing; only the 4-byte
  bucket array is reallocated and rehashed. Partial-order data lives in a side
  array allocated only in that mode.
- **`StateKeyCodec`**: the store keeps a compact key - a plain item is 2 bytes
  (biased x, y; 0xFF,0xFF once gone), a fish or plug 3 (plus its flags byte) -
  instead of 5 bytes per model. The invariants that make this lossless are checked
  on every encode and throw if broken.
- **Stale entries** (review P5): a state reached again more cheaply is updated in
  place and re-queued; the dearer queue entry is skipped on pop. The old code
  expanded it again. This alone trims a few expansions even at weight 1 (a
  consistent heuristic guarantees the optimal cost at expansion, not at
  generation): start 217,622 -> 217,606, wreck 756,029 -> 752,746. Stored states,
  answers and bounds unchanged.

Result: **39-61 bytes per state (0.25-0.37x)**, same speed. Society, serial:
69.6 M expansions / 94 M states in 480 s at 4.1 GB, f 86 -> 92, no stall past 2^25.

## P2 — skipping the round for moves that change nothing else

Turns and swims into open water from under nothing were 70-75% of move attempts and
80-89% of `ApplyMove` time, each running a full round to conclude that nothing
happened. `Room.FastPath.cs` applies them directly when the room is fresh and no
corpse is counting down: a turn flips the facing; an inert step (destination empty,
only wall resting on the fish, no goal model touching an edge - the only case where
a step can change who may leave) moves the fish. The file's header carries the
argument for why the skipped round is provably empty.

Not reproduced: `TouchDir` is not cleared on every model as a real round would.
It is write-only for physics and already excluded from the state key and digest.

Guarded by `Physics_FastPathMatchesFullRound` - two rooms walked in lockstep on all
81 corpus and 11+ micro levels, 6,000 moves each, compared field by field and cell
by cell - plus the unchanged physics digests and the 80 reference solutions.
`Room.UseFastPath` turns it off for such comparisons.

Result: **1.5-2.1x** per expansion, serially.

## P4 — parallel expansion

`SolveOptions.Threads` (CLI `--threads`, default all cores for `solve`, 1 per level
for `solve --all`, 1 for `bench`). Nodes popped from one f-bucket form a batch;
phase 1 simulates their successors on per-thread rooms (producing compact key,
hash, move, estimate, without touching shared state); phase 2 merges serially in
batch order. At weight 1 this is the serial expansion order exactly, so
`ParallelSolverTests` asserts identical answer, expansions, generated and stored
counts against `Threads = 1` - which is why the serially measured baseline stands
for parallel runs. Plain A* only: `--work`/`--stuck`/`--partial-order` keep shared
caches and run serially.

## Combined (12 cores, .NET 11 JIT, best of 3, vs the post-C1-C7 build)

| level | before (k exp/s) | serial P1+P2 | 12 threads | memory |
|---|---|---|---|---|
| start | 257 | 2.06x | **5.93x** (1,525 k/s) | 0.28x |
| cannons | 135 | 1.81x | **6.01x** | 0.30x |
| wreck | 210 | 1.77x | **5.93x** | 0.37x |
| society (1.5 M cap) | 147 | 1.49x | **5.29x** | 0.26x |
| library (2 M cap) | 163 | 2.04x | **5.89x** | 0.25x |

Society end to end: 70 M expansions (95 M states, f=92) in **110 s** - the original
stalled at 24.8 M and f=86 regardless of budget.

## Open

- Phase 2 (merge) is serial and now the bound on scaling: ~3x from 12 threads on
  top of the serial gains. Sharding the store by hash would parallelise it, at the
  cost of the exact serial order (and with it the identical-counts guarantee).
- `MacroSolver`, `ItemSolver` and `WindowOptimizer` still use `StateSet` and run
  serially; they get the fast path for free (it is in `Room`).
- The heuristic remains the lever for proofs: society's bound moved 86 -> 92 for
  a bundled 110-move solution.
