# 016 — .NET 11, and JIT beats Native AOT for long searches

All five projects now target `net11.0` (the editor `net11.0-windows`);
`scripts\build-solver.ps1` and the README ask for the .NET 11 SDK. No code
changes were needed: clean build with no new warnings, all 578 tests green,
and the micro-level baseline (docs/015) unchanged — expansion counts are
identical, as they should be for a runtime upgrade.

## Measured (Snapdragon X Elite, win-arm64)

Same workloads, deterministic expansion counts, 3 alternating runs each:

| workload | net10 JIT | net11 JIT | net10 AOT | net11 AOT | net11 AOT `IlcInstructionSet=native` |
|---|---|---|---|---|---|
| cannons (215 k exp.) | 1.8 s | 1.8 s | 2.0 s | 2.0 s | — |
| wreck (756 k exp.) | 3.7 s | 3.6-3.7 s | 4.2-4.3 s | 4.1-4.2 s | 4.2 s |
| society, 1.5 M exp. | 10.1-10.4 s | 10.1 s | 12.3-12.4 s | 12.1-12.2 s | 12.0-12.1 s |

- **.NET 11 vs 10: 0-2%** — within noise. The release's JIT work (more bounds-check
  elimination, `!=` loop cloning, redundant branch removal, generic-virtual
  devirtualisation) targets patterns this code barely has; the hot path is the
  physics' recursive, branchy rule checks.
- **JIT is 15-20% faster than Native AOT** on every search longer than a second,
  on both runtimes. Dynamic PGO (on by default in the JIT) profiles the real
  branch and call behaviour; AOT compiles without it, and targeting this CPU's
  instruction set does not close the gap. AOT keeps its startup win (docs/001's
  70 ms vs 355 ms `verify --all`), so the README now recommends the exe for quick
  commands and the JIT build for long runs - reversing its earlier advice.

## What .NET 11 offers that could matter later

- C# 15 (`LangVersion=latest` picks it up). Nothing in it targets this code.
- Bounds-check elimination now covers `i + cns < len`, `(uint)i < len` implying
  `i >= 0`, and coalesced constant-index accesses - worth keeping in mind when
  writing the P2 fast path: plain span loops in those shapes now compile check-free.
- Runtime async, interface-dispatch helpers for AOT, FP16, SVE2 intrinsics:
  irrelevant here (no async, no interfaces or vectors in the hot path).

## Open

- The AOT gap is a measured fact on this machine, not a cause. If AOT matters
  again (distribution), profile both builds on the same run before guessing.
- The performance work that can matter is algorithmic (review P1/P2/P4), not the
  runtime version.
