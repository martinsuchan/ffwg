# 031 — `smooth`: solutions that read like a person's (2026-11-23)

The shortcuts the window optimiser finds (docs/029, 030) are shortest, but they look
machine-made: the fish take turns on nearly every move. barrel 1195, moves 305–315,
had `DdDdDdDdDd`, five moves down for each fish, alternating. A person plays that as
`DDDDDddddd`. The A* solution of duckie has 19 fish switches; the game's original has 7.

`ffsolve smooth` keeps the length and changes only the order of the moves.

## How it works (`FishFillets.Search/SolutionSmoother.cs`)

It rests on the same fact as the window splice. Two settled states with equal
`Room.WriteStateKey` keys are interchangeable. So a segment from state X to state Y
can be replaced by any other segment from X to Y that is no longer. Each change is
checked by replaying only the changed segment from its saved start state and comparing
the key at its end. At the end, the whole solution is replayed to Solved.

1. **The original's moves where they fit.** The solution is traced (the key before
   and after every move), and so is the reference, the game's original from
   `legacy/solution/old`.
   - A DP over the solution's positions chooses, for each stretch, between:
     - its own moves;
     - a segment of the reference that starts and ends in the same two states and
       is no longer.
   - The DP prefers, in order: shorter, then more moves from the reference, then
     fewer moves changed. The last rule is what makes a second run change nothing.
   - The reference segments are then locked.
   - The DP looks only 8 matched positions ahead, which keeps it linear.
2. **Fewer fish switches in what is left.** Greedy passes over the unlocked stretches,
   with segments of at most 48 moves. A change is one of:
   - a run of one fish swapped with the next run of the other (`D d D d` → `D D d d`);
   - one move shifted by 1–8 places (a shift of 1 is a plain swap, which also
     covers `luuu` / `uuul`).

   A change is kept only when:
   - every move in it is possible;
   - the state at the end of the segment comes out the same;
   - the trace then passes through **more of the reference's states**, or the same
     number with **fewer fish switches**.

   Each kept change strictly improves that pair, so the passes end.
3. Steps 1 and 2 repeat until neither changes anything. A reordering can create new
   states shared with the original, and step 1 then takes those over.

The tool does no search, and the work is polynomial in the length. Every level
takes well under a second.

only 5 states. At the start and the end, the two are not the same moves in another
order; they differ in the moves themselves. The original ends `RRRDDDDDDD…` and ours
ends `URDDDDD…`. Reordering cannot turn one into the other, and making them match would
need a search for a different 96-move solution.

## Identical items (2026-11-24)

On map, the smoothed solution still read differently from the original in many
places: one fish lifted an item and then the other fish lifted another, where the
original did it the other way round. The reason was in the keys, not in the steps.
From move 463 on, our solution and the original move **identical items** into each
other's places: models 13, 14, 19 and 21 are the same item, and at the end each
stands where another one stands in the original. With plain keys the two traces
then never share a state again, so nothing after move 463 could come from the
original.

The smoother's keys now merge identical items, the way the A* search does
(`ItemSymmetry`, docs/022). Within each class of identical items the 5-byte key
fields are sorted. This is sound for the same reason as in the search: the physics
cannot tell such states apart, which `SymmetrySound` checks state by state on every
micro-level and fuzz room.

| map | before | after |
|---|---|---|
| moves from the original | 22 % | 75 % |
| states shared with it | 453 | 1527 |
| fish switches | 143 | 175 (the original has 175) |

There are more fish switches because the result now follows the original's order of
fish. What is left outside the original are the 17 stretches where our solution is
shorter, so the original's moves cannot fit there. No other level changed: none of
them had identical items that traded places.

## Tests (`SmoothTests`)

- **Every improved solution:** the result still solves the level and is no longer.
  It has no fewer moves from the original and no fewer shared states; with those
  equal, no more fish switches. A second run changes nothing.
- **An original smoothed against itself** stays exactly as it is.
- **An interleaved stretch** (`AAA bbb` → `AbAbAb`, placed where it still plays out
  and ends in the same state, on hole, barrel, map, linux and start): smoothing
  against the original restores the original exactly; without a reference, the fish
  switches go back to at most the original's.

- **Identical items that traded places** (map) still match the original: over 70 %
  of the moves come from it, and over 1400 states are shared.

The full suite passes (1248), with the micro baseline and the physics digest unchanged.

## Open

- From now on a new improvement is smoothed before it is promoted: verify, smooth,
  verify again, write.
- The greedy steps miss orders that are reachable only through a worse
  intermediate order. A bounded search for the "best-looking" equal-length segment
  between two shared states would find more, duckie in particular, at search cost.
